# Wall-in-One v0.4.2: stills Wall-in-One makes, and Workshop files trusted less

Pre-alpha release. Pair it with **Wall-in-One companion v0.3.1** for Noctalia
5.2 and later (plugin API 32), whose panel links now open the Library
([Companion](#companion-v031)). Wall-in-One runs on Wayland; X11 sessions are
not supported.

**Check your web wallpapers and presets after updating.** A Wallpaper Engine
item's still, and the colours made from it, now comes only from Wall-in-One
or from you: never from a picture the item's author shipped. Web wallpapers
and presets of them get their preview as a still only with the new setting
**Use a web wallpaper’s own preview as its still** (Settings → Library, under
Allow web wallpapers). It is on if 0.4.1 allowed web wallpapers, so nothing
changes for those profiles. With it off, give such an item a still by hand
in its settings; until you do, it is left out of playlists
([Stills](#stills-wall-in-one-makes-or-you-pick)).

## Stills Wall-in-One makes, or you pick

- **Where a Wallpaper Engine item's still comes from.** Either Wall-in-One
  makes it from the item itself, or you pick it. Wall-in-One makes it with the
  engine's screenshot of a scene, or ffmpeg's frame of a Workshop video. The
  `preview` picture in an item's `project.json` is the author's file, so it
  is no longer used unless you allow it (below). See
  [Wallpaper Engine items](../wallpaper-engine.md#stills).
- **A preset of a scene** gets the engine's screenshot of its scene with the
  preset's own settings, like any scene. It no longer comes from the preset's
  preview.
  - **It is left out of playlists until that screenshot exists.** Wall-in-One
    takes it automatically after a library scan, so open Wall-in-One once after
    updating. It needs linux-wallpaperengine and a display size it can measure.
    Restarting the wallpaper service alone does not take it. Until then the
    preset's card says it has no still to show yet. If the engine runs and
    gives no screenshot, the app says so once for each batch of presets it
    tries, and tries them again the next time it starts; pick a still for the
    preset in its settings instead.
- **A web wallpaper, or a preset of one,** has no still of its own: the
  engine's screenshot of a web page is taken before the page has painted. The
  new setting **Use a web wallpaper’s own preview as its still** takes it from
  the item's preview, as 0.4.1 did.
  - It works only while Allow web wallpapers is on, and is greyed out
    otherwise; its saved value is kept.
  - Upgraded profiles that allowed web wallpapers have it on.
  - New profiles, and every other profile, have it off.
  - With it off, pick a still in the item's settings. The new interface's
    Library inspector says so, and there is no Regenerate.
  - A preset whose own `project.json` says `web` counts as one while web
    wallpapers are off, even over a scene: it doesn't play until they are on.
- **A picture named like a Workshop video** (`foo.png` beside `foo.mp4` in
  Steam's Workshop folder) is no longer that video's still.
- **Nothing is deleted.** 0.4.1's preview-made stills stay in
  `Automatic Stills`, hidden as before. A web wallpaper's, or a web preset's,
  is used again if you turn the setting on; a scene preset's is replaced by
  its new engine still (once that is taken, above) and no longer used.
- Thumbnails in the library still show each item's preview: that is a
  picture of the item, not your wallpaper.

## Pairing files are trusted by where they are

- **Only a sidecar in your library folders is read.** A
  `<video>.wall-in-one.json` beside a video could name any picture on the
  computer as that video's still. Wall-in-One writes these only inside your
  library folders, and only to name a still that is there too.
  - A sidecar is read only when the video's folder and the picture it names
    both resolve inside a library folder (symbolic links and `..` followed),
    and one naming a still Wall-in-One made only while that still's
    `Automatic Stills` is one it looks in (below).
  - Any other sidecar is ignored, as though there were none.
- **A Workshop item's sidecar is never read**, even inside a library folder.
  Wall-in-One decides what is Workshop content by where it is (Steam's
  Workshop folder on any drive, or a folder with a `project.json`), not by
  how the scan labelled it.
- **An ignored sidecar no longer stops a still.** Wall-in-One leaves it
  untouched and publishes its own still beside it, without a record.
  - **Until it has, that video is left out of playlists**, like a preset of a
    scene: one whose sidecar names a picture outside your library folders (for
    example after you narrowed a library folder in 0.4.1, whose stills then lay
    outside it), and a Workshop video whose sidecar its author shipped. The app
    makes the new still after a library scan, so open Wall-in-One once after
    updating; restarting the service alone does not.

## Workshop files are not local media

- **A library folder that covers Steam's Workshop folder** no longer lists a web
  wallpaper's `preview.gif` and the other files in an item's folder as your
  own videos and pictures, which 0.4.1 then thumbnailed and drew stills from
  with web wallpapers off.
  - A file under Steam's Workshop folder is left to the Workshop scan.
    **If Wallpaper Engine scanning is off,** a Workshop video that 0.4.1 listed
    through a library folder covering Steam's folder is therefore no longer in
    the library: its playlist entries say so, and nothing is removed. Turn on
    Wallpaper Engine scanning (Settings → Library), the source meant for those
    items: it lists them again, at the same paths, with the same stills and
    entries. A Workshop video in a Steam library that Steam's own list of
    libraries doesn't name is not listed at all now.
  - A folder with a `project.json` is an item folder, and everything below it
    is the item's: nothing in its subfolders is listed, whatever `project.json`
    files they hold. The item folder lists only the video its `project.json`
    names, if it is a video; a web page, an application, any other type, or
    one that can't be read, lists nothing.
    **If videos of yours are gone from the library,** a `project.json` in
    their folder or in one above it is why; the app doesn't say so. Add a
    subfolder that holds no `project.json` as a library folder of its own
    (it lists its files), or move the videos out of the item folder.
- **No still is taken from a library folder's `Wall-in-One/Automatic Stills`
  that a Workshop item could have shipped,** and none is made there: one in a
  library folder that is an item folder or lies in one of Steam's items, or
  one reached through a link out of its library folder. 0.4.1 paired whatever
  picture there had a still's name, and followed a link there. A library folder
  that is Steam's `431960` folder itself keeps its stills.
  **If such a folder is your first library folder,** the stills 0.4.1 made in
  it are left on disk and no longer used. New ones are made in the next library
  folder that is not one (Settings marks it), or none if no folder is one, and
  Regenerate then says why.
- **ffmpeg is told what it may open.** Frames, thumbnails and downloaded
  previews are taken with only the `file` protocol (and `pipe`) and only
  picture and video containers, so a playlist named like a picture or a
  video is refused, not followed to other files or the network. Files are
  handed to it already opened, never by name (a wallpaper's or a Workshop
  item's file is not opened through a link, at its name or in place of its
  folder), and downloaded previews arrive
  on stdin, so a name such as `preview%01d.png` is not read as a numbered
  sequence of other files. Nor is the name it writes to: a cache folder with
  `%` in its name no longer stops every thumbnail.

## Every engine start checks the item's type

- **The service reads a Workshop item's type before it starts the engine,
  with web wallpapers on too.** In 0.4.1 it did so only while they were off.
  So with them on, "an executable wallpaper is never run" rested on the scan.
  An `application`, an unknown type, or an item whose `project.json` is
  missing, unreadable, malformed, over 256 KiB or found in no Workshop folder
  is now refused and skipped, web wallpapers on or off.
- **So does the app,** wherever it starts linux-wallpaperengine itself (taking
  a still, and the legacy applier). The check is inside the two functions
  that start the engine, so no new caller can miss it.

## Fixes

- **The Library's Select button shows its icon** instead of a blank square.
- **A library folder reached through a link higher up its path gets its
  stills.** With `~/Videos` a link to another disk and `~/Videos/Wallpapers`
  a library folder, every still failed, silently, since 0.1.0: its videos and
  scenes had none and stayed out of playlists. Their stills are made at the
  first library scan after the update, so that one does more than usual: a
  frame from each video, and the engine's screenshot of each scene. Inside a
  library folder a link is still never written through, and a folder that
  refuses a still is now said once.

## What sits out until you open Wall-in-One once

The first document compiled after the update (by the service's start, before
the app is opened) leaves out each preset of a scene without a still you
picked, each video whose only still came from a sidecar 0.4.2 ignores, and
each video or scene whose only still was in a library folder's `Automatic
Stills` a Workshop item could have shipped (above).
A playlist that holds only such items plays nothing until then. If your
default playlist is one of them, the service plays All media instead, and a
schedule rule that names one is left out (its hours play the default); the
service's log says so. Nothing is rewritten:
`settings.toml`, `schedules.json`, `displays.json` and `playlists.json` keep
their references, which work again once the app has made the stills.

## Updating

- **From 0.4.1:**
  1. Update the app and its service definitions.
  2. Restart the wallpaper service and open Wall-in-One once, in either order.
     (The Arch setup script restarts a running service itself unless run with
     `--no-enable`, and says so; then you open the app.) Opening the app makes
     the new stills that each preset of a scene, and each video whose sidecar
     is now ignored, needs to play
     ([above](#what-sits-out-until-you-open-wall-in-one-once)); restarting the
     service alone does not, so until the app has been opened they sit out of
     playlists. Restart the service promptly: until it restarts, the one still
     running is 0.4.1's. Before its definitions are reloaded, the app leaves
     web wallpapers paused; after that, with web wallpapers on, the old
     service starts them without the type check, as 0.4.1 did.
  3. Update the companion to v0.3.1, then restart Noctalia (or turn the
     plugin off and on in Noctalia's plugin settings): until then its
     **Open Wall-in-One** link keeps opening the Store.
  4. Look for web wallpapers and presets without a still (if the new setting
     is off) and pick one for each you want to keep in your playlists.
- **From 0.4.0 or older:** read the [0.4.1 release notes](v0.4.1.md) first.
- **Updates are one-way:** going back to an older version afterwards is not
  supported. 0.4.1's Settings go read-only when `settings.toml` has the new
  `web_wallpaper_previews` key. It is written only when its value differs from
  what its absence means (the value of Allow web wallpapers): turning the new
  setting on with web wallpapers off, or off with them on, turning web
  wallpapers on in a new profile (the setting stays off), or turning Allow web
  wallpapers off in an upgraded profile (the setting stays on).
