# Wall-in-One v0.3.0: the new interface is the default

Pre-alpha release. The companion is unchanged: **Wall-in-One companion v0.2.1**
for Noctalia 5.2 (plugin API 32) is still the paired version. Noctalia hosts at
API 17–31 keep installing companion v0.1.3. The exact companion commit is
recorded in `flake.lock`.

## The new interface, now the default

Wall-in-One now opens the redesigned interface, with every page in it:
- **Library:** the details pane edits as classic does.
  - **Colours:** palette and light or dark.
  - **Stills:** choose one, regenerate a scene's, or reset to defaults; Try again for a wallpaper that stopped playing.
  - **Changes:** remove, add to a playlist, bulk favourite, add a folder.
  - **Keys:** classic's shortcuts.
- **Store:** Wallhaven and MotionBGS.
  - **Filters:** they sit inline, never in a popup.
  - **Results:** 40 per page.
  - **Downloads:** one at a time, into your first library folder, plus "Download & apply".
- **Playlists:** create, rename, duplicate and delete. Add several wallpapers at once, drag entries by their handle to reorder, and undo an entry's removal. Each playlist has its own interval and shuffle.
- **Schedule:** a week calendar, with rules in priority order. "Now" and "Why?" come from the wallpaper service itself.
- **Displays:** the monitor layout, and what each display shows and why. A display can have its own playlist for when nothing is scheduled, its own Cycle and Shuffle, and a choice of which display the desktop colours follow.
- **Settings:** every classic setting, searchable, with a palette manager.

Window-level behavior:
- **First run:** a welcome screen asks for your library folder, and offers to import older data. "Not now" saves nothing.
- **After an update:** the one-time Tidy up card.
- **Errors:** runtime errors appear as notices; a session log in Settings has a "Hide file paths" switch.

The full guide is [docs/interface.md](../interface.md).

**The classic window:**
- **To go back:** choose Classic in Settings → Appearance → Interface. The choice is saved and applies from the next start.
- **For one start:** `wall-in-one --ui=classic` opens classic without saving anything. `--ui` is now listed in `wall-in-one --help`.
- **If the new interface doesn't open:** start `wall-in-one --ui=classic` and choose Classic in Settings → Appearance → Interface. See [If the new interface doesn't open](../updating.md#if-the-new-interface-doesnt-open).

## Also new

- **Noctalia template row** (new Settings → Colours). It shows whether Wall-in-One's colour template is installed in Noctalia, and why if it isn't.
  - **Install or Repair:** a button you press, never automatic, using the existing backups. It is refused while an upgrade is unfinished.
  - **Render the colours now:** a separate button. It asks Noctalia to re-render **all** of its templates, not only Wall-in-One's, and says so.
- **Palette names can't clash.**
  - A copy gets a free name: "Nord copy", then "Nord copy 2".
  - The new editor checks the name as you type.
  - Saving refuses a name any palette you can pick already uses: built-in, community or yours, ignoring case.
  - This also fixes the classic palette browser silently overwriting one of your own palettes.
- **Checked before any removal or folder change.** Removing a wallpaper, removing a library folder, or turning off Wallpaper Engine scanning is first tried against a copy of your library.
  - **When it's refused:** if the change would leave a playlist in use with nothing to play, the app refuses it.
  - **What the refusal says:** it names the playlist and the still that would go, e.g. "rain.mp4 plays through forest.png, which this removes".
  - **Where it applies:** both interfaces, `ctl`, and the background service.

## Fixes

- **References by name are kept.** Since 0.1.x, a saved default playlist, schedule rule or display assignment that named its playlist by **name** was reset or deleted at every start. That happened in hand-edited and some older profiles. These references now keep working, and are given the playlist's id.
- **A playlist with nothing to play is refused on every path.** Before, a playlist with nothing that plays could stop every new setup from reaching the wallpaper service. That includes an unused playlist holding only videos still waiting for their stills. Now these are refused:
  - every change that would make such a playlist the default, or use it in a rule or a display assignment;
  - every change that would leave such a playlist behind;
  - in both interfaces, from `ctl`, and in the background service.
- **A removed file is never named in a new setup.** Each removal is followed by a real library scan, and only that scan is published. Until it lands, the last setup stays.
- **Failures end cleanly.** If that scan fails, or the setup can't be written (for example permission denied, or a document too large):
  - the app says so in a notice, and keeps the last setup;
  - edits are still saved, and reach the wallpaper service once a scan succeeds;
  - Quit still completes, also after the last window was closed.
- **No more internal lock-file paths in messages.** A removal that has to wait for a download or capture says so in plain words, and the path goes to the log.
  - Error messages also name the real folder now. Before, some named an internal `/proc/self/fd/…` path. Where the folder is no longer known, the message says "(a folder Wall-in-One had open)".
- **A copy that can't play is refused.** Copying "All wallpapers", or any playlist, is refused if the copy would hold only wallpapers playback can't use. Before, such a copy could stop every later setup from reaching the wallpaper service.
- **Forget Display and playlist rename say exactly what they saved.** Each reads every file it will change first, and changes each one in a single save. If a later step fails, the message says what was saved and the setup is updated with it. Before, a partial failure said "nothing changed".
- **Forget Display keeps a newer colours choice.** It clears which display the desktop colours follow only if they still follow the display being forgotten and the displays are still mirrored. Before, it could erase a colours choice made just before it, and switch independent displays back to mirrored.
- **Playlist changes wait for the library to be up to date.** After a removal or a library-folder change, until the library has been scanned again, a playlist change that takes wallpapers from the library or depends on what plays is refused with "wait for the library scan to finish", and nothing is saved. That covers copies, additions, Undo, entry removal, still changes, and putting a playlist into a rule, a display or the default. Before, a copy or a `ctl playlist-add` made in that moment could name a removed file and stop every later setup from reaching the wallpaper service.
  - This holds in the background service too.
  - If the library folders change while a removal is running, the removal's own scan isn't used: the library is scanned again from the new folders.
- **A file that can't be read is left alone.** Removing from, editing, or adding to a store file the app can't read (for example, a permissions problem) is refused with a clear message, and the file isn't touched.
  - Before, a removal could report success while doing nothing, and some `ctl` commands replaced your favourites, playlists or still choices with a one-item file.
  - A file with damaged contents is still recovered as before: set aside as `.broken`, and replaced.
- **"Saved" is never reported as "nothing changed".**
  - If a save reaches the disk but its folder can't be synced, every store, the settings, `ui.toml`, palettes and Tidy up say it was saved but not confirmed, in one message with the rest of the action's result.
  - If a step after a save fails (for example, `ctl select` saving your pick and then failing to start it), the reply says "Saved, but it couldn't be applied", and what was saved is published. A change that saved nothing gets its ordinary error instead.
  - If a damaged file was set aside but its replacement couldn't be saved, the message says where the original was kept.
  - If the one-time backup before a file's format upgrade was written but couldn't be confirmed, the upgrade is refused, the file is left as it was, and the message says the copy stays.
  - The classic window's wallpaper menu shows these messages in full, backup location included.
- **A newer settings change is never lost to an older one.** If a settings save reached the disk but couldn't be applied while you made another change, the newer change was dropped, and a default playlist could be left half-set. Now each change is saved in turn, and the app says once which settings were saved but couldn't be applied.
- **Nothing is left stuck "in progress".** An unexpected error no longer leaves anything waiting until a restart, in either window. That covers:
  - Quick choice;
  - the schedule rule editor ("Saving…") and the default playlist;
  - display settings;
  - a palette or key save, and the palette editor;
  - Playlists ("Saving…");
  - a Store download card ("Downloading…") and the Store's results pager;
  - installing the Noctalia template;
  - Tidy up;
  - a Settings check ("Checking…");
  - the library scan and the upgrade check.

  If a save went through, the app says so. If it didn't, the window goes back to showing what is saved before it reports the error.
- **An interrupted save never deletes anything it can't prove is its own.** When an interrupted save, download, still or Noctalia template install or repair leaves a file behind:
  - **A file it can't prove is its own is kept.** Before, on filesystems that record file times only to the second, the cleanup could delete an edit made to the same file at that moment.
  - **A copy that was briefly in place is kept too.** It is moved intact into a hidden `.wall-in-one-retained` folder beside it, never truncated.
  - **The message names where the file is.** If that folder can't be read, the message says the location couldn't be checked; it never says the file is gone.
- **Files 0.2.2 left behind are never cleaned up automatically.** 0.2.2 could leave a download under a temporary name after a failed save, and that file could hold your edits. The day-old cleanup used to empty it.
  - This version's own partial downloads use new temporary names, and only those are cleaned up after a day.
  - Tidy up lists what 0.2.2 left and offers to archive it, intact.
  - A provider's info file whose wallpaper is gone is kept intact in `.wall-in-one-retained`, never emptied.
- **A removal that doesn't go through keeps the wallpaper's download record.** Before, removing a downloaded wallpaper emptied its record first, so a removal that then failed left the wallpaper counted as a local file.
  - The record is now set aside whole, put back if the removal doesn't finish, and found again by 0.3.0 after a crash. (If 0.2.x starts next instead, see [Going back](../updating.md#going-back-from-030-to-022-021-or-020).)
  - A read-only wallpaper is refused before anything is changed.
- **"Couldn't look" is never taken for "gone".** When a folder or file can't be looked at (a permissions problem, a disk error), the app keeps what may still be there and says it couldn't be checked. That covers:
  - removing and trashing a wallpaper;
  - Tidy up's lists, its archive and Undo;
  - the cleanup of old captures after an update.

  Before, some of these treated it as missing: a removal could be reported as done, Undo could be withdrawn, and an old capture could be discarded.
- **A change made outside the window is never written over.** A window can stay open while `settings.toml` or a playlist file is changed by hand, by `ctl`, or by a setup that manages those files. These now go by what is saved at that moment, not by what the window read when it opened:
  - **Library folders.** Adding or removing a folder, or choosing where downloads go, changes that one thing. Before, the window saved its own older list, and a folder added outside it was dropped.
  - **Deleting or renaming a playlist.** Whether it is the default is read again, also when the default names it by name. Before, a default saved outside the window could be left naming a playlist that was just deleted.
  - **"Is anything using this playlist, and can it still play?"** is asked of what is saved, at the moment of the change.
  - **The palette editor** doesn't save over a palette file changed since it opened it.
  - If a file such a check needs can't be read, only the change that depends on it is refused, and the message names the file.
- **A file moved aside is confirmed on disk before the original counts as gone.** This applies when a file is moved into `.wall-in-one-retained`, into a removal's holding folder, or back. If that can't be confirmed (a full disk, for example), the message says so and names where the file is. Before, a power cut at that moment could lose a kept copy on some filesystems.
- **A removal interrupted by a full disk is finished or undone, never left half done.**
  - The message says the move couldn't be confirmed. Before, it said the file had "changed".
  - The next library scan or start finishes the removal, including the wallpaper's still and the small file that records it. Before, those were left behind.
  - If the wallpaper itself was never touched, its download record is put back. Before, the record could be left in a hidden folder, and the wallpaper was treated as a local file from then on.
- **A download still in progress is not cleaned up as abandoned.** The day-old cleanup and Tidy up skip a partial download that a running Wall-in-One still holds, also when the clock jumps forward or two copies of the app run at once.
- **Settings that can't be saved are handled all-or-nothing.** Some setups keep the configuration folder read-only. There:
  - Deleting the default playlist, or renaming one the default names by name, is refused before anything changes. Before, the playlist was deleted, the default was left naming nothing, no new setup reached the wallpaper service, and the next start never loaded the library.
  - A default that names a playlist by name is shown as the default on every page. A default that names no playlist is left out: "All media" plays, the app says once which file and key to change, and `--write-config` and the service's startup check print a warning and carry on.
  - See [A settings file that can't be saved](../settings.md#a-settings-file-that-cant-be-saved).
- **A state folder that can't be written no longer leaves the app "checking" forever.**
  - With the state folder and its files read-only, the app now opens, loads the library, and refuses each change with its own reason.
  - Where the profile can't be opened at all, the app says why, every refused change gives the same reason, and Try Again or a restart checks again. Before, every change answered "still opening; retry shortly" until the folder was fixed.
- **A failure that keeps happening is said once.** With the state folder read-only, "Could not save wallpaper playback availability" was shown and logged every two seconds. It is now said once, and again only if the reason changes or a save has worked in between.
- **A still that can't be made because its folder is read-only is said as that.** The app names the folder and how many wallpapers are affected, once per folder. Before, nothing was said.
- **A wallpaper folder that is a link:**
  - Picking a link in the folder chooser adds the real folder it points to, and says so. Before, the link was saved, nothing in it was scanned, and nothing said why the library was empty.
  - A link already saved in `settings.toml` is left as it is. Its row in Settings says it isn't scanned and which folder to add instead.
- **Noctalia's folder reached through a link works.** Installing, repairing or removing the palette template there no longer ends with "its recovery cleanup remains", and no lock file is left behind.
- **Read-only folders are named as that.** Installing the palette template into a state folder that can't be written, and Tidy up archiving a leftover from a folder that can't be written, now say the folder can't be written. Before, they said "cannot verify … No such file" and "changed meanwhile".
- **Tidy up shows more of what is kept.** It lists copies kept beside your wallpapers and in each wallpaper folder, the files a crash can leave during a download, and any folder it couldn't look into. A copy kept in a folder that no longer holds a wallpaper isn't listed.
- **Closing the classic window while it checks or imports older data now quits.**
- **`--write-config` says exactly which files it wrote,** or that nothing changed. Renderers installed in standard places now give the same paths whether you run it from a terminal or the service runs it.
- **Empty temporary folders left behind by discarded files are removed.**
- **Names containing `&`, `<` or `>` show correctly everywhere.** In both windows, rows, banners, toasts and messages built from your names, paths, or a provider's text could show blank or garbled, for example a schedule rule named "Frog & toad".
- **The wallpaper service:**
  - Each reply to a client has a one-second write limit, so a stuck or slow client can't hold up the service.
  - The startup check for another running service can't hang.
  - A very large hand-written configuration no longer makes the status reply fail. Its status leaves out the oldest records of skipped wallpapers, and says how many it left out. The status format the companion reads is unchanged.

## Behavior that changed

These are refusals, each with a reason:
- **A default playlist with nothing to play is refused,** in either interface. Settings changed in the same moment are rolled back with it.
- **`ctl schedule-add` and `ctl display-assign` refuse an empty playlist.**
- **Adding a video that has no still yet:**
  - the new interface doesn't offer it, and refuses it;
  - classic and `ctl` refuse it only into an empty playlist.
- **Removing a library folder:**
  - in the new interface, it asks first; your files stay on disk either way;
  - it is refused if a playlist needs what that folder holds.
- **Removing a wallpaper has no Undo,** as before. Its favourite, colours and playlist entries go with the file.
- **Copying a playlist is refused** when the copy would hold nothing that plays.
- **Any change to a store file that can't be read is refused.** Before, some removals silently did nothing, and some additions replaced the file.
- **Playlist changes made while the library is being rescanned are refused.** This applies after a removal or a folder change, and the refusal asks you to wait for the scan. Over `ctl` the refusal's kind is `library-not-current`.
- **Deleting a playlist is refused while `settings.toml` can't be read,** or is malformed. The app can't check whether that playlist is the default. Over `ctl` the refusal's kind is `unreadable`. With no `settings.toml` at all, deleting works as before.
- **Removing a read-only downloaded wallpaper is refused** before anything changes.
- **Removing or trashing a wallpaper that can't be looked at** says it couldn't be checked. Over `ctl` the kind is `local-io`, where it used to be `missing`.
- **Tidy up waits while one of its archives can't be read.** Archiving the old palette template, and Undo for a change that archive may hold, are blocked with the reason and the folder's path. Moving the damaged folder out of `tidy-archive` unblocks them; its Undo goes with it.
- **Partial downloads 0.2.2 left behind are no longer removed after a day.** Tidy up lists them.
- **Changes that depend on a file the app can't read are refused.** Over `ctl` the kind is `unreadable`, and the reply names the file:
  - a change that would leave a playlist with nothing to play, while `settings.toml`, the schedule file or the displays file can't be read or is damaged;
  - a change that asks what a playlist holds, and removing a library folder, while the playlists file can't be read or is damaged.
- **Deleting the default playlist, or renaming one the default names by name, is refused while `settings.toml` can't be changed.** Over `ctl` the kind is `local-io` when the file can't be saved, and `read-only` when it holds settings this version doesn't know.
- **Picking a wallpaper folder that is a link adds the folder it points to.**
- **A removal that couldn't be confirmed on disk stays pending.** The next library scan or start finishes it, or undoes it if the wallpaper itself was never touched. Over `ctl` the kind is `local-io`.

Two outputs changed:
- **`--write-config`** prints one line per file (`wrote:`, `removed:`, or `nothing changed: …`). Scripts that parse its output may need updating.
- **Renderer lookup:** the app looks for mpv and linux-wallpaperengine in standard places first, then in the rest of your `PATH`. The standard places are Nix store directories on `PATH`, your Nix profiles, `~/.local/bin`, `/usr/local/bin`, `/usr/bin` and `/bin`. See `docs/runtime-config.md`.

## Files: what changes and how to go back

There are no new file formats. `settings.toml` keeps 0.1.4's keys, and `runtime.toml`'s shape is unchanged.

**`ui.toml`:** the interface choice is now saved whichever interface you pick, Classic included. It uses the same version 2 file, with its one-time `ui.toml.v1-backup`, as 0.2.2's choices did. Until you choose, nothing is saved, and the default (now New) opens.

**Per-playlist interval and shuffle, and a display's playlist that beats the shared rules:** these use `playlists.json` / `displays.json` version 2 and `runtime-overrides.toml`.
- 0.2.0 introduced these formats.
- 0.3.0 is the first release whose interface sets them.
- The first change keeps a one-time `.v1-backup` of each file.

**Going back to 0.2.2, 0.2.1 or 0.2.0:** see [Going back from 0.3.0](../updating.md#going-back-from-030-to-022-021-or-020). In short:
- **0.2.2** honours a saved New. A saved Classic is dropped the next time 0.2.2 saves a window preference, and 0.3.0 then opens New again.
- **0.2.1 and 0.2.0** start classic, and read a version 2 `ui.toml` without saving it.
- **One case can't be told apart:** if you tried New in 0.2.2 and then went back to Classic, 0.2.2 saved nothing. So 0.3.0 opens the new interface once. Choose Classic in its Settings and it stays classic.
- **Downloads:** 0.3.0 uses new hidden temporary names (`.wall-in-one-v2-…` and `.wall-in-one-commit-…`). 0.2.2 doesn't see them: its cleanup, its library scan and its Tidy up all leave them alone.
- **What 0.3.0 kept for you, 0.2.2 may still clean up.** 0.2.2's own day-old cleanup empties files left under its old temporary names. To keep them, archive them in Tidy up before going back.

## Updating

**From 0.2.x:** update the app and refresh its service definitions as usual. There is no companion update.

**From 0.1.4:** follow the [update guide](../updating.md), the same as for 0.2.0.

## Test scope

Every check in the flake passed on the release commit, including:
- **Packaged GUI tests:** 1,568 of them, including:
  - a 375-case failure test. It fails each step of a removal in turn, and the configuration write, against Quit, Next, edits, more removals and a closed window;
  - 200 seeded random orderings of those events.
- **Upgrade and downgrade:** the golden-profile and v0.1.4 downgrade suites.
- **VMs, both on Noctalia 5.2:** the desktop VM, which now drives the new interface, and the real-package update/rollback VM.
- **Released 0.2.2 against this version:** tests run the released 0.2.2 code, interrupt it at each step, edit what it left behind, and then run this version over it. They cover downloads, stills, the stores, the Noctalia template, the cleanup of old captures, unfinished removals and the older-data import. They also go to 0.2.2 and back, run both versions at once, fill the disk at each step, move the clock, and make the configuration, state or wallpaper folder read-only.

The release candidate went through eight rounds of independent review, then six full pre-release reviews. The medium issues those reviews found are fixed, along with the smaller bugs found alongside them, and each fix was reviewed again before it was merged. After the sixth, the project's own tests went looking for more bugs of the same kinds, and what they found is fixed too. A final full review is in progress.

These remain outside the checks:
- physical multi-monitor behavior;
- broad GPU and driver coverage;
- a live scene capture on a desktop session;
- case-insensitive filesystems;
- a real read-only mount (the tests use folder permissions), and network filesystems;
- power loss;
- long-running desktop use.
